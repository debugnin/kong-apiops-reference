# APIOps Pipeline — Application Team Onboarding Guide

> **Audience:** Application development teams onboarding a new service to Kong Gateway.
>
> **What you need to know about Kong:** Almost nothing. You own one spec file and one generated file. The platform team decides which of your routes get authentication or rate limiting, and does so without ever editing your files.

---

## How It Works

| What | Where | Who edits it |
|---|---|---|
| Your API specification | `services/<your-service>/openapi.yaml` | You |
| Generated Gateway Service + Routes | `services/<your-service>/kong.yaml` | Generated by `make generate` — don't hand-edit |

`make generate` reads your OpenAPI spec and produces `kong.yaml` — the Gateway Service with all of its Routes nested inside, exactly as decK produces them. `make merge` then combines that with the platform team's plugin files into one Kong configuration, and `make sync` applies it.

### Ownership boundary

```
┌─────────────────────────────────────┬──────────────────────────────────────┐
│  Application team owns              │  Platform team owns                  │
├─────────────────────────────────────┼──────────────────────────────────────┤
│  services/<svc>/openapi.yaml        │  platform/kong/plugins/*.yaml        │
│  services/<svc>/kong.yaml (gen)     │  platform/kong/consumers/consumers.yaml│
│                                      │  Makefile                            │
└─────────────────────────────────────┴──────────────────────────────────────┘
```

This repo ships two example services playing the application-team role: `bookings` and `kongair-flights`, both pointed at `https://httpbin.konghq.com`. They're referenced throughout this guide as worked examples.

**Important:** `key-auth` and rate limiting are opt-in per route, not opt-out — if your routes need either, you'll need the platform team to add an entry for them in `platform/kong/plugins/`, naming your route. If they don't, nothing further happens. The one exception is plugins the platform team has made genuinely global (currently `correlation-id`, for request tracing) — those apply to your service automatically, with nothing for you to ask for.

## Step 1 — Point your spec at your upstream

Set `servers[0].url` in your `openapi.yaml` to your backend's URL:

```yaml
servers:
  - url: https://my-service-backend.example.com
```

Both example services in this repo hardcode `https://httpbin.konghq.com` — there's no per-environment substitution needed for a single, stable upstream.

---

## Step 2 — Add your service

### Directory structure

```
services/
└── my-service/
    └── openapi.yaml        ← your API spec (the only file you write by hand)
```

Create the directory and file under `services/`. The folder name should be lowercase, hyphen-separated (e.g. `kongair-loyalty`, `kongair-check-in`).

### Example

**`services/kongair-loyalty/openapi.yaml`**

```yaml
openapi: "3.1.0"
info:
  title: KongAir Loyalty
  version: "v1"
servers:
  - url: https://httpbin.konghq.com
paths:
  /v1/members/{id}/points:
    get:
      operationId: getMemberPoints
      summary: Get a loyalty member's points balance
      tags:
        - Loyalty
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
      responses:
        "200":
          description: Points balance
        "404":
          description: Not found
```

## Step 3 — Generate `kong.yaml`

```bash
make generate
```

This creates (or regenerates) exactly one file for your service, `services/kongair-loyalty/kong.yaml` — the Kong Gateway Service (host, protocol, port) with one Route per operation in your spec nested inside it.

Route names follow the pattern `<ServiceName>-<operationId>` — for the example above, `KongAir_Loyalty_API-getMemberPoints`. **Write down this exact name** if you need to ask the platform team to attach a plugin to it.

Commit the generated file along with `openapi.yaml`.

---

## Step 4 — Decide whether you need a plugin, and ask for it by route name

You do not add plugins yourself — but you do decide whether your route needs one, and you ask for it by its exact generated name.

| If your route... | Tell the platform team to add it to |
|---|---|
| Returns or modifies a specific user's/customer's data | `platform/kong/plugins/key-auth.yaml` |
| Is a state-changing write (POST/PUT/PATCH/DELETE), or a high-traffic public read | `platform/kong/plugins/rate-limiting.yaml` |
| Is public, read-only, low-traffic, or just a CORS preflight (`OPTIONS`) | Neither — no entry needed |

For example, asking for `key-auth` on the loyalty endpoint above means the platform team adds exactly this to `key-auth.yaml`, and nothing else changes:

```yaml
  - name: key-auth
    route: KongAir_Loyalty_API-getMemberPoints
    config:
      key_names:
        - apikey
```

Your `kong.yaml` is never touched to make this happen — the plugin file is the only thing that changes.

## Step 5 — OpenAPI spec requirements

| Rule | Detail |
|---|---|
| Use OpenAPI 3.x | 3.0.x or 3.1.x are both supported |
| Every operation needs a unique `operationId` | Becomes part of the generated Kong route name — duplicates cause `make generate` to fail |
| `operationId` must be unique across all services | Conflicts across services cause `make merge` to fail |
| `servers[0].url` must be set | Your upstream's base URL |
| Include all paths your service exposes | Routes are generated 1:1 from paths in the spec |

## Step 6 — Validate, then open a PR

```bash
make validate     # merges your new files with everything else, offline
git add services/kongair-loyalty/ platform/kong/plugins/   # if a plugin was added for you
git commit -m "Add kongair-loyalty service"
git push origin feature/add-kongair-loyalty
```

Open a pull request. CI runs `make diff` to show the control-plane impact before merge.

---

## Step 7 — Remove a service

```bash
git rm -r services/kongair-loyalty/
# also remove any entries referencing its routes from platform/kong/plugins/*.yaml,
# otherwise `make validate` will fail on a broken foreign key
git commit -m "Remove kongair-loyalty service"
```

`make validate` will tell you immediately if a plugin file still references a route you just deleted — fix that in the same commit.

## Validating locally before pushing

```bash
# Install deck + yq (one-time)
curl -sL https://github.com/kong/deck/releases/download/v1.55.0/deck_1.55.0_linux_amd64.tar.gz | tar -xz
sudo mv deck /usr/local/bin/

make generate   # regenerates kong.yaml for every service
make validate   # merges everything and checks it offline
```

Common errors caught here:
- Duplicate `operationId` values
- Invalid path parameter definitions (parameter in path but not declared)
- A plugin file referencing a route name that no longer exists

## Common mistakes

| Mistake | What happens | Fix |
|---|---|---|
| Duplicate `operationId` across operations | `make generate` fails | Make every `operationId` unique across all your paths |
| Duplicate `operationId` across services | `make merge` fails | Prefix with service name in the spec, or rename the operation |
| Hand-editing `kong.yaml` | Changes are silently lost next time someone runs `make generate` | Edit `openapi.yaml` instead and regenerate |
| Forgetting to remove plugin entries when deleting a service | `make validate` fails with a broken foreign key | Remove the matching entries from `platform/kong/plugins/*.yaml` in the same PR |

## Getting help

| Question | Contact |
|---|---|
| `make validate` is failing and you're not sure why | Platform team — share the exact error, it names the broken file/field |
| Want `key-auth` or rate limiting on a route | Platform team — give them the exact route name from your `kong.yaml` |
| Need a new environment or control plane | Platform team |
| OpenAPI spec validation errors | Check deck output; refer to deck docs at https://developer.konghq.com/deck/ |
